# Правила работы агентов в Nemo

Этот файл — единственный источник общих инструкций для AI-агентов проекта.
Ролевые конфигурации в `.agents/agents/` дополняют, но не переопределяют его.

## Перед началом работы

1. Прочитать `docs/CURRENT_STATE.md`.
2. Для архитектурных, security, release и инфраструктурных задач прочитать
   `docs/ARCHITECTURE_AUDIT.md`.
3. Для production или публикации исходников свериться с
   `.agent/artifacts/prod_readiness_plan.md` и
   `.agent/artifacts/GIT_MIGRATION.md`.
4. Не считать исторические файлы в `.agent/artifacts/.archive/` и
   `.agent/artifacts/docs-archive/` источником текущих требований.

## Поиск и понимание кода

- Если доступен `codebase-memory-mcp`, сначала использовать его graph tools для
  функций, классов, маршрутов и зависимостей.
- Для строк, конфигураций, Docker, shell и Markdown использовать `rg`/`rg
  --files`. Если `rg` отсутствует, использовать `grep`/`find`.
- Не утверждать, что graph, MCP или другой инструмент использован, если он не
  был доступен в текущей сессии.
- Перед изменением понять вызывающий и вызываемый код, schema и связанные
  security rules.

## Границы архитектуры

- Основное направление frontend-зависимостей: `UI/hooks → services →
  repositories → PocketBase/adapters`.
- Repository не должен импортировать feature/UI-код или создавать сетевое
  соединение как side effect импорта.
- PocketBase schema, hooks и TypeScript contracts изменяются согласованно.
- Все операции с пользовательскими данными проверяют ownership или membership
  на сервере. Клиентская проверка не является авторизацией.
- Для PocketBase filters использовать parameter binding, если API его
  поддерживает; не собирать filter из пользовательского ввода.
- Hooks PocketBase могут требовать локальный `require` внутри изолированного
  handler. Проверять это на используемой версии PocketBase.

## Privacy и security

- Никогда не добавлять секреты, токены, реальные пароли, приватные ключи,
  production emails/IP или содержимое `.env` в Git, logs, документацию и test
  fixtures.
- При обнаружении похожего на рабочий секрет остановить его распространение и
  сообщить о необходимости ротации.
- Не ослаблять PocketBase rules, CORS, CSP, Tauri capabilities или network
  exposure без явного описания угрозы и согласования.
- Push/LiveKit gateway считается внутренним сервисом. Server-to-server вызовы
  должны быть авторизованы; LiveKit token выдаётся только после server-side
  membership check.
- Обычные сообщения/media должны шифроваться на клиенте до отправки. Не делать
  заявлений о проверенном E2EE, пока crypto interoperability tests не проходят.
- Одноразовые комнаты не используют обычные PocketBase collections, MinIO,
  task queue, durable logs и backups. Существующий `isPrivate/isEphemeral` не
  считается реализацией этого режима.
- Не логировать plaintext сообщений, полный push endpoint, auth token и
  чувствительные идентификаторы без необходимости.

## Код и документация

- TypeScript остаётся strict. Не добавлять `any`; на границах использовать
  `unknown` с проверкой или конкретные типы.
- Следовать действующим Biome/TypeScript правилам проекта, не вводить новые
  стилевые запреты только из вкусовых предпочтений.
- Пользовательская и проектная документация пишется по-русски. Имена API,
  типов и стандартов можно оставлять на английском.
- Комментарии объясняют причину или ограничение, а не повторяют код.
- `docs/CURRENT_STATE.md` описывает подтверждённое состояние и явно отделяет
  целевые требования от реализации.
- После архитектурного изменения обновить соответствующий план и документацию.

## Тестирование

- Работать по `docs/TESTING_PLAN.md`.
- Текущие тесты частично устарели. Нельзя удалять падающий тест только ради
  зелёного CI: сначала определить, устарел test double или найден реальный bug.
- Unit tests не должны подключаться к Dev/Prod API.
- Для frontend-команд использовать рабочую директорию `app`:
  `npm run lint`, `npm run build`, `npm test -- --run`.
- Перед завершением изменения запускать проверки пропорционально риску и точно
  сообщать, что прошло, упало или было пропущено.

## Инфраструктура и release

- Deployment VPS выполняется только вручную по SSH. Не добавлять GitHub Actions
  или webhook с доступом к VPS без отдельного явного решения владельца.
- Домашний development deploy может оставаться автоматизированным, но workflow
  не должен получать больше прав, чем необходимо.
- Не использовать mutable `latest` для воспроизводимого production release.
- Реальные operational configs и публичные self-hosting templates разделяются.
- Не запускать destructive команды с невалидированными путями. Не предлагать
  `git push --force` как стандартный release flow.
- Не изменять файлы непосредственно на домашнем сервере, если их обновляет Git:
  правка выполняется в репозитории, затем deploy. Секретные `.env` остаются вне
  Git и изменяются вручную.

## Гигиена работы

- Сохранять пользовательские незавершённые изменения и не выполнять
  `git reset --hard`, `git checkout --` или массовое удаление без разрешения.
- Для правок файлов использовать точечные изменения. Форматтер допустим для
  механических изменений в согласованном scope.
- Временные файлы создавать в системной временной директории либо
  `.agent/temp_scripts/` и удалять после использования.
- `.agent/artifacts/` предназначен для согласованных планов и результатов, а не
  для каждого промежуточного отчёта.
- RTK можно использовать, если он установлен и не скрывает нужный diagnostic;
  обязательным он не является.
