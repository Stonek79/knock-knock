# ADR-0003 — Owner-only чтение users и capability DTO для профилей

**Статус:** Принято для Dev-среза; runtime-приёмка не завершена  
**Дата:** 2026-08-14

## Контекст

Auth-коллекция `users` содержит не только имя и аватар, но и служебные поля,
приглашения и публичные ключи. Правило «любой авторизованный пользователь может
читать users» поэтому является слишком широким. Клиентский фильтр или UI-проверка
не заменяют серверную авторизацию.

## Решение

- В зафиксированном snapshot `users.listRule` и `users.viewRule` ограничены
  собственной записью обычного пользователя: `@request.auth.id != "" && id =
  @request.auth.id`.
- Публичный поиск, contacts и получение E2EE-ключей используют отдельные custom
  routes с явными allowlist DTO; `publicExport()` не используется.
- Capability endpoint ключей сам проверяет self/public/shared-room capability и
  не выдаёт неполные ключи.
- Клиентские consumers больше не читают чужие `users` напрямую: профиль peer
  берётся из contacts DTO, ключи — из capability endpoint. Собственное частичное
  состояние ключей читается только для собственного id и нужно для repair.
- Все найденные фильтры с пользовательскими или производными идентификаторами в
  изменённом срезе переведены на PocketBase parameter binding.

## Почему не открываем users «только ради ключей»

Открытие коллекции возвращает вместе с ключом весь auth-record и создаёт новый
риск при добавлении полей в schema. Узкий серверный DTO сохраняет минимальный
контракт и оставляет проверку membership на сервере.

## Операционные ограничения

Схема применяется владельцем через Dev PocketBase Admin UI и затем экспортируется
в `infra/home/pb_schema.json`. Отдельная migration-инфраструктура в этом Dev-only
срезе не вводится. Git rollback откатывает snapshot и код, но не изменяет уже
работающую БД; её правило владелец возвращает через Admin UI или пересозданием
Dev-базы.

Агент не подключается к Dev/Prod API или базе. Runtime-проверка двумя обычными
пользователями остаётся обязанностью владельца и является условием закрытия
acceptance; Prod и release readiness этим ADR не закрываются.

## Последствия и остаточные риски

Поиск private-профилей и прямое чтение чужого профиля становятся недоступны — это
ожидаемое fail-closed поведение. Нужны ручной Dev-прогон authorization matrix,
проверка route-level auth и дальнейшие независимые P0/P1 срезы (crypto
interoperability, media, presence, calls и release readiness).
