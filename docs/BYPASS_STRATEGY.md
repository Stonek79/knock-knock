## 1. Анонимизация и обход ФЗ-149

Для вывода проекта из-под действия п. 10 ст. 8 ФЗ-149 (обязательная авторизация через Госуслуги, СМС на паспортные данные или российские ID-системы) необходимо юридически и технически исключить связь владельца ресурса с юрисдикцией РФ.

### 1.1. Сокрытие владельца домена
* **Регистратор**: Использование анонимного зарубежного регистратора, такого как **Njalla** (домен оформляется на компанию регистратора, выступающую в качестве прокси) или **Porkbun** с оплатой криптовалютой (BTC, Monero, USDT).
* **Доменная зона**: Исключить зоны `.ru`, `.su`, `.рф`, `.moscow` и т.д. Рекомендуется использовать нейтральные международные TLD: `.net`, `.org`, `.cc`, `.me`, `.xyz`, `.im`.
* **Настройки Whois**: Полное включение функции Whois Privacy (Privacy Protection) для сокрытия контактных данных.

### 1.2. Юридическое позиционирование
* Сервис позиционируется как международное приложение, разработанное группой независимых инженеров (без упоминания российских граждан/компаний).
* Пользовательское соглашение ([docs/RULES.md](file:///Users/alexstone/WebstormProjects/knock-knock/docs/RULES.md)) и политика конфиденциальности оформляются на английском языке (или двуязычном) с указанием применимого права нейтральной юрисдикции.

## 2. Архитектура обхода блокировок (Сравнение вариантов)

Для того чтобы российские пользователи могли беспрепятственно общаться, данные должны находиться в безопасности, а каналы связи — маскироваться.

### Сравнительный анализ архитектурных схем

| Критерий | Вариант 1: FRP + Nginx на VPS + VPN (Hiddify) на Домашнем (Текущий рабочий) | Вариант 2: Cloudflare Tunnel (cloudflared) | Вариант 3: Двухнодовый VPS (За рубежом + РФ) |
|---|---|---|---|
| **Где хранится база PocketBase** | Дома у владельца в РФ (за роутером) | Дома у владельца в РФ (за роутером) | На дешевом VPS в РФ дата-центре |
| **Стоимость** | Низкая ($3-5/мес за зарубежный VPS) | Бесплатно (только покупка домена) | Низкая (~$5-7/мес за 2 VPS) |
| **Сложность настройки** | Средняя (настройка FRP + Nginx + VPN клиент) | Низкая (одна команда запуска демона) | Средняя (настройка Xray + прокси) |
| **Устойчивость к блокировкам РКН** | **Максимальная** (Трафик FRP завернут в Hiddify VPN) | Низкая (РКН рвет TLS-хэндшейки Cloudflare туннелей с ошибкой EOF) | **Высокая** (Reality между VPS) |
| **Уровень приватности данных** | **Максимальный** (физический доступ к серверу только у вас) | Средний (Cloudflare терминирует SSL-трафик) | Средний (хостинг-провайдер в РФ имеет доступ к диску) |
| **Задержка (Latency)** | Средняя (~100-150 мс) | Средняя (~80-120 мс) | Низкая (~40-80 мс) |

---

### Детальное описание Рекомендуемого варианта (FRP + Nginx + VPN)

**Почему отказались от Cloudflare Tunnel и чистого FRP:**
* **Cloudflare Tunnel (`cloudflared`)** полностью блокируется провайдерами через системы DPI/ТСПУ по отпечатку TLS-соединения (`TLS handshake EOF`), даже при использовании VPN.
* **Чистый FRP (Fast Reverse Proxy)** без VPN обрывается провайдером каждые 40 секунд, так как DPI определяет долгоживущее TCP-соединение нетипичного протокола к зарубежному серверу и сбрасывает его.

**Архитектура решения:**
```
[Пользователь из РФ] 
      │ 
      ▼ (HTTPS запрос к домену whoami.ninja через Cloudflare Proxy)
[VPS Ninja за рубежом (Nginx)]
      │
      ▼ (Локальный порт: 3000, 8090, 9090)
[FRP Server (frps)]
      │
      ▲ (Зашифрованный FRP туннель)
      │
      ▼ (Завернут в Hiddify VPN/happ для обхода DPI)
[FRP Client (на домашнем ноутбуке)]
      │
      ▼ (Локальный проброс)
[PocketBase / Web]
```

1. **VPS Ninja (За рубежом)** выступает в качестве точки входа. Nginx принимает запросы по HTTP (80) после Cloudflare (Flexible SSL) и перенаправляет их в локальные порты FRP-сервера по доменному имени.
2. На этом же VPS запущен **FRPS**, который ожидает зашифрованные подключения.
3. **Домашний сервер (Ноутбук)** запущен за NAT. На нем работает **FRPC** (FRP Client) в Docker.
4. На ноутбуке работает клиент Hiddify (happ / VPN). Он полностью скрывает факт использования FRP от провайдера, оборачивая его трафик в свою маскировку (VLESS/Reality), предотвращая обрывы соединений.
5. Для внешнего SSH-управления (вне дома) FRP также пробрасывает локальный порт 22 домашнего сервера наружу (порт 6000 на VPS Ninja). Доступ осуществляется по ключу `id_home_server`.

## 3. Миграция инфраструктуры за рубеж

Перенос бэкенда за роутер или смена юрисдикции требует адаптации других компонентов системы.

### 3.1. Сервис Push-уведомлений (`push-gateway`)
* **Текущая схема**: [infra/home/push-gateway/index.js](file:///Users/alexstone/WebstormProjects/knock-knock/infra/home/push-gateway/index.js) использует `web-push` для отправки уведомлений на шлюзы Apple (APNs) и Google (FCM).
* **Специфика миграции**: 
  * Сам микросервис `push-gateway` должен быть развернут **на зарубежном VPS**. 
  * Если `push-gateway` оставить на домашнем сервере в РФ, ТСПУ РКН может заблокировать его запросы к серверам Google/Apple, и пуши перестанут доходить до мобильных устройств.
  * PocketBase на домашнем сервере ставит задачи отправки пушей в `task_queue`, cron-воркер выгребает их и делает исходящий POST-запрос через VLESS-Reality туннель на зарубежный IP `push-gateway` (например, `http://127.0.0.1:4000/api/send-push`, проброшенный через Rathole).

### 3.2. Почтовый сервис (SMTP)
* **Текущая схема**: Использование Brevo SMTP (`smtp-relay.brevo.com`).
* **Специфика миграции**: 
  * Brevo имеет строгие комплаенс-правила и блокирует трафик, связанный с РФ. 
  * **Решение**: Развернуть собственный легковесный почтовый сервер (например, **Mailcow** или **Postal**) в Docker-контейнере на зарубежном VPS. Это гарантирует независимость от санкций. Альтернативно можно использовать лояльные к крипте SMTP-сервисы (например, Flowroute, SMTP.com), оплачиваемые USDT.

### 3.3. Воркеры и фоновые задачи (Workers)
* Все фоновые задачи PocketBase (очистка сообщений, рассылки, обработка очереди), описанные в [tasks.pb.js](file:///Users/alexstone/WebstormProjects/knock-knock/infra/home/pb_hooks/tasks.pb.js), выполняются встроенной cron-системой PocketBase.
* Поскольку PocketBase в Рекомендуемом варианте крутится на домашнем сервере, воркеры выполняются локально (в РФ) без сетевых задержек при работе с SQLite-базой.

## 4. Мультиплатформенность и встроенный прокси (Tauri v2)

Для сборки нативных приложений под **Windows, macOS, Linux, Android и iOS** используется фреймворк **Tauri v2**. Он позволяет использовать текущий веб-стек (React + TS + CSS) и оборачивать его в нативный бинарный контейнер с бэкендом на Rust.

### 4.1. Схема интеграции нативного прокси на Rust

Главная проблема нативных приложений в РФ — блокировка домена бэкенда. Если пользователь запускает приложение на телефоне или ПК без включенного системного VPN, приложение не сможет связаться с сервером.

Для решения этой проблемы в бэкенд приложения (Rust-слой Tauri) интегрируется легковесный клиент обхода блокировок:

```
[React UI (Webview)]
       │
       ▼ (Запрос к http://127.0.0.1:local_port)
[Tauri Rust Backend]
       │
       ▼ (Интегрированный клиент Shadowsocks / VLESS-Reality)
[Шифрованный туннель через ТСПУ]
       │
       ▼
[VPS за рубежом (Entrypoint)] ──> [PocketBase]
```

1. **Rust-бэкенд Tauri** при запуске приложения генерирует случайный локальный порт и запускает в отдельном потоке (native thread) встроенный клиент обхода блокировок (например, библиотеку `shadowsocks-rust` или `xray-core` в режиме клиентского прокси).
2. **React UI (фронтенд)** настраивается на работу с API-адресом `http://127.0.0.1:local_port` (или использует прокси-конфигурацию Webview).
3. Все сетевые запросы приложения к бэкенду PocketBase автоматически заворачиваются Rust-слоем в защищенный туннель и уходят на зарубежный VPS.
4. **Отказоустойчивость звонков (WebRTC)**: Звонки в реальном времени (WebRTC/LiveKit) не должны идти через прокси во избежание задержек. Rust-слой Tauri настраивает Webview так, чтобы STUN/TURN и медиа-трафик шли напрямую (bypass-правила для IP-адресов LiveKit сервера).

## 5. In-App Proxy для Web/PWA версии

Если пользователь заходит в Knock-Knock через обычный браузер (без установки нативного приложения), мы не можем запустить нативный Rust-процесс. Для веб-версии используется прикладной WebSocket-туннель.

### 5.1. Реализация через Service Worker

```
[Браузер: React UI]
       │
       ▼ (Обычный fetch API запрос)
[Service Worker (sw.ts)] ── (Перехват запроса)
       │
       ▼ (Упаковка в бинарный кадр)
[WebSocket / WebTransport Соединение] ── (Маскировка под чат-сокет)
       │
       ▼ (Прохождение сквозь ТСПУ РКН)
[VPS за рубежом (Nginx + WS Proxy)]
       │
       ▼ (Локальный HTTP запрос)
[PocketBase]
```

1. **Service Worker** ([app/src/sw.ts](file:///Users/alexstone/WebstormProjects/knock-knock/app/src/sw.ts)) перехватывает все сетевые запросы `fetch` к API PocketBase.
2. Вместо отправки обычного HTTP-запроса (который заблокирован в РФ), Service Worker упаковывает заголовки и тело запроса в бинарный формат и отправляет их через уже открытое постоянное **WebSocket** (или WebTransport) соединение.
3. Это WebSocket-соединение маскируется под стандартный сокет реального времени для обмена сообщениями в чате, поэтому РКН не блокирует его (блокировка веб-сокетов сломает работу большинства интерактивных сайтов).
4. Зарубежный прокси-сервер принимает WebSocket-кадр, эмулирует локальный HTTP-запрос к PocketBase, получает ответ, упаковывает его обратно в WebSocket и отправляет клиенту.
5. Service Worker принимает ответ из сокета и возвращает его фронтенду в качестве стандартного ответа `Response`. Фронтенд даже «не знает», что запрос прошел через туннель.
