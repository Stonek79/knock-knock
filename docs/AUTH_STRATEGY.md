# Аутентификация, регистрация и уровни профиля

> **Статус:** локальный hook/schema contract согласован вокруг `invites.token` и
> проверяется fail-closed; расходование использует условный атомарный `UPDATE`.
> Dev runtime matrix и проверка конкурентного расходования ещё не выполнены;
> release остаётся заблокированным. См.
> [ARCHITECTURE_AUDIT.md](./ARCHITECTURE_AUDIT.md).

## 1. Разделение понятий

- **PocketBase account** — техническая учётная запись и сессия постоянного
  пользователя.
- **Profile level** — продуктовые правила видимости и допустимых контактов.
- **Ephemeral identity** — временная identity внутри отдельной одноразовой
  комнаты; не является обычным PocketBase account.

## 2. Текущее состояние

Frontend использует username/password и invitation input. PocketBase выдаёт
обычную auth-сессию. В schema есть `profile_type = public|private`.

Локальная модель использует `token`, `room`, `expires_at`, `max_uses` и
`uses_count`. Регистрационный invite имеет пустую `room`, комнатный invite —
непустую. Входное поле клиента по обратной совместимости называется
`invite_code`, но hook ищет только `token` и сохраняет в user только id записи.
Прямое чтение `invites` закрыто; room-проверка идёт через авторизованный DTO
endpoint, возвращающий узкий allowlist `RoomInvitePreviewDto` без `token` и
`created_by` (тип используется в repository/service/`useJoinRoom`). Локальные
valid/expired/exhausted/foreign/malformed tests и contract-тесты validate
endpoint проходят, но Dev runtime и конкурентная атомарность расходования ещё
не подтверждены в развернутом runtime: локальный consume использует общий
условный атомарный `UPDATE` с проверкой `rowsAffected()`, поэтому конкурентное
использование одного invite не должно превышать `max_uses`. Образ PocketBase
не закреплён, а Dev concurrent matrix ещё не выполнена владельцем.

До применения snapshot в Dev и runtime-проверки регистрация не готова для
публичного доступа.

Ошибки регистрации не показывают пользователю сырой ответ PocketBase. Известные
состояния invite (`required`, `invalid`, `expired`, `used`, `unavailable`) имеют
отдельные локализованные сообщения; неизвестная ошибка получает нейтральный
fallback. Backend-совместимость, типы контекста и UI-ключи разделены в
`app/src/lib/constants`, `app/src/lib/types` и `app/src/lib/utils`; мэппер всегда
возвращает только типизированный ключ локализации. Для сетевого сбоя показывается
отдельное сообщение о недоступности сервера. На странице вступления сетевой сбой
также отделён от недействительной или истёкшей ссылки, без раскрытия
существования invite.

## 3. Целевая регистрация постоянного аккаунта

1. Клиент отправляет username/password и invite token по HTTPS.
2. Сервер проверяет token до создания записи пользователя.
3. Проверка работает fail-closed: любая ошибка означает отказ.
4. Token хранится в недоступной для list/view коллекции и используется только
   через custom endpoint/hook.
5. Проверяются TTL, число использований и персональная привязка, если она задана.
6. Создание пользователя и расходование invite выполняются атомарно.
7. В logs не попадают token, password и email/username без необходимости.

Email не является обязательным внешним идентификатором закрытого профиля. Если
email используется для открытого профиля или recovery, это отдельное явно
включаемое продуктовое решение.

## 4. Уровни профиля

### Открытый

- минимальный публичный DTO доступен для поиска;
- можно принимать приглашения только от открытого уровня;
- закрытые группы открытых пользователей не становятся глобально видимыми.

### Закрытый

- не появляется в глобальном list/search;
- не раскрывает email, username или другие внешние идентификаторы;
- использует внутренний регистрационный ID и выбранный псевдоним;
- персональные и групповые комнаты состоят только из закрытых профилей.

### Одноразовый

- создаётся персональным one-use invite внутри volatile runtime;
- может иметь автоматически созданный или выбранный временный username;
- не создаёт обычную запись `users` и не получает долгоживущий PocketBase token;
- не поддерживает multi-device;
- живёт не дольше комнаты и reconnect lease.

Межуровневые ограничения проверяются сервером при создании комнаты, приглашении
и присоединении. Фильтрация только в UI недостаточна.

## 5. Сессия постоянного пользователя

- auth token хранится минимально необходимое время;
- refresh lifecycle запускается после login, а не только при первом mount;
- logout закрывает realtime и очищает user-scoped keystore, Outbox, history,
  media cache, Query cache и CacheStorage;
- локальные базы и cache keys включают endpoint и `userId`;
- смена аккаунта на одном устройстве не получает доступ к данным предыдущего.

## 6. Recovery

Recovery допустим только для постоянных профилей и требует:

- versioned backup format;
- парольное шифрование с утверждённым KDF;
- импорт тех же алгоритмов и usages, которые создаёт production keygen;
- integrity check и понятную ошибку неверного пароля;
- interoperability test на чистом устройстве.

Приватные ключи могут покидать keystore только внутри явно созданного
зашифрованного backup. Поэтому нельзя описывать их как «никогда не покидающие
устройство» без этого уточнения.

## 7. Security acceptance tests

- регистрация без invite, с expired/used/wrong invite отклоняется;
- invite нельзя перечислить или прочитать напрямую;
- закрытый профиль не раскрывается list/search;
- невозможно создать смешанную комнату разных постоянных уровней;
- logout и account switch изолируют локальные данные;
- refresh работает после login и корректно останавливается после logout;
- ephemeral identity отсутствует в PocketBase и backups.
