# Текущее состояние Nemo

> Единственный актуальный снимок развернутой архитектуры и согласованных
> требований. Реализация одноразового режима ещё не завершена — разделы с его
> правилами являются целевым контрактом, а не заявлением о готовой функции.
> Старые планы и
> пошаговые инструкции ниже могут содержать исторические решения и не являются
> источником истины.

## Размещение сервисов сейчас

### Домашний сервер

- `whoami-pb-dev` — Dev PocketBase, порт хоста `9090`;
- `whoami-pb` — текущий Prod PocketBase, порт хоста `8090`;
- `nemo-minio` — MinIO, API и консоль доступны только через `127.0.0.1`;
- `whoami-frpc` — исходящий FRP-клиент; соединение с VPS проходит через
  локальный Happ/Xray SOCKS (`127.0.0.1:10808`) и дополнительно защищено FRP
  TLS;
- Mailpit — только для разработки.

Dev и текущий Prod используют отдельные PocketBase-хранилища и отдельные
MinIO bucket’ы (`nemo-dev` и `nemo-prod`) с разными service account.

### VPS

- Nginx — единственная публичная HTTP(S)-точка входа;
- FRP server — принимает туннель от дома;
- LiveKit — звонки и WebRTC media;
- Push gateway — серверная отправка push и выдача LiveKit-токенов.

Перенос Prod PocketBase на VPS — будущий этап, а не текущая deployed-схема.
Маршрут VPS `127.0.0.1:19000` → домашний MinIO уже запущен и проверен HTTP
health request. Сейчас он не делает Prod PocketBase на VPS развернутым.

11 августа 2026 года восстановлен доступ к Dev/Prod PocketBase через FRP после
инцидента с периодическими `heartbeat timeout`. Перезапуск FRPC при добавлении
MinIO впервые применил ранее добавленную конфигурацию SOCKS вместе с
`tls.enable = false`; после возврата `tls.enable = true` новый FRPC-сеанс
успешно вошёл на FRPS и публичный Dev API снова стал доступен. Однако новый
сеанс получил `proxy already exists`, поэтому немедленное восстановление могло
обслуживаться старой регистрацией. Результат фикса, длительная стабильность и
корректное освобождение старых proxy-регистраций ещё проверяются.

## Три режима профиля

### Открытый профиль

Профиль доступен для поиска и приглашений. Общение и группы открытого уровня
состоят только из открытых профилей.

### Закрытый профиль

Профиль не имеет внешнего идентификатора. Внутри приложения используется
регистрационный ID и псевдоним. Общение разрешено только с закрытыми профилями.
Текущий frontend применяет безопасное отображение: настоящее имя и аватар
показываются только для явно открытого `profile_type`; закрытый или неизвестный
тип получает нейтральное имя и без аватара. Экран входящего звонка не показывает
технический `roomId`. Передача выбранного зашифрованного псевдонима закрытого
профиля пока не реализована.

### Чтение профилей и capability DTO (локальная реализация)

В коде и schema snapshot реализован owner-only доступ к `users`: обычный
пользователь напрямую читает только собственную запись. Поиск, contacts и
получение публичных ключей проходят через отдельные allowlist DTO и server-side
capability checks; peer-профиль больше не запрашивается прямым `users.getOne`.
Фильтры invite/search и другие изменённые динамические фильтры используют
parameter binding.

Invite registration локально согласована с snapshot schema вокруг единого
`invites.token`: регистрационный invite не содержит room, комнатный invite
содержит room; TTL и max uses проверяются fail-closed. Прямой list/view invites
закрыт, а проверка room invite выполняется через авторизованный POST DTO
endpoint с token в body, не в URL.
Локальные contract tests проходят, но preprod runtime matrix и проверка
конкурентного расходования invite ещё не выполнены.

Проверка room invite возвращает узкий allowlist DTO `RoomInvitePreviewDto`
(`id`, `room`, `expand.room`, `expires_at`, `max_uses`, `uses_count`) без
`token`, `created_by` и прочих внутренних полей; тип используется в repository,
service и `useJoinRoom`. Добавлены детерминированные local contract-тесты
validate endpoint (valid, expired, exhausted, без room, несуществующая комната,
отсутствие `token` в ответе, allowlist полей) без подключения к API.

Конкурентное расходование invite теперь проходит через общий helper
`invite_consumption.js`: регистрация и room join выполняют условный атомарный
`UPDATE` в PocketBase SQLite (`uses_count < max_uses`) и принимают решение по
`rowsAffected()`. Локальный contract-тест проверяет, что первый расход получает
слот, а следующий получает отказ без over-subscription. Это закрывает прежний
`get -> check -> save` в коде, но не является доказательством фактического
runtime: образ PocketBase всё ещё `latest`, поэтому владелец должен закрепить
версию, применить hook/schema snapshot и прогнать двухпользовательскую
concurrent matrix в preprod. См. план `docs/plans/p0-4-invite-registration.md`.

Локальная задача конкурентного расходования invite закрыта: дальнейшая работа
по этому пункту — только ручная preprod runtime-приёмка, а не доработка кода.

Локальный срез P0.3b также обновлён после review: прямой доступ к presence
закрыт, клиент использует server-owned маршруты и безопасный polling вместо
подписки на закрытую коллекцию; собственный DTO возвращает только id своей
записи, а shared/typing DTO используют room-scoped `user_id` как correlation
key, не как auth-доказательство. Media upload читает MIME/размер из multipart
upload-события и fail-closed отклоняет отсутствующий/некорректный размер,
основной файл protected и ограничен верхним размером. Room-less broadcast
media выдаётся только через auth-маршрут с server-owned marker и filesystem
stream; обычная create/update-загрузка не может подделать этот marker, а frontend загружает
файл bearer-запросом в Blob URL (включая lightbox, audio и document paths).
Join звонка проверяет принадлежность `call_log_id` той же комнате, инициатор не
может принять собственный ringing-call до запроса LiveKit, и допускается только
ringing/ongoing переход; статусный маршрут проверяет роль
инициатора/приглашённого участника; call push-задача явно получает тип `push`.
Contract tests этого среза проходят локально. Это не заменяет runtime
authorization matrix, проверку реального PocketBase file endpoint и
двухклиентскую проверку звонков в preprod.

Это пока не означает, что срез принят в работающем preprod-контуре: Admin UI rule
и двухпользовательская authorization matrix должны быть проверены владельцем
отдельно. Агент к Dev/Prod API или базе не подключался. Release `NO-GO` и
остальные P0/P1 остаются открытыми.

### Разбивка PocketBase hooks (локальная проверка)

Монолит `infra/home/pb_hooks/main.pb.js` разделён на модули `main.01`–`main.08`
(lifecycle, registration, message delivery, scheduled tasks, admin broadcast,
user capabilities, invites, room-read) и чистые helper-модули (`db.js`,
`users_dto.js`, `task_helpers.js`, `hook_constants.js`, `request_utils.js`).
Единый файл удалён. Порядок загрузки задаётся именами файлов, каждый callback
подключает зависимости локальным `require`, ни один `*.pb.js` не импортирует
другой. Это проверено локально (`node --check`, hook static/contract tests,
`npm run build`, `npm run lint`, frontend suite, `git diff --check`), но Dev
runtime smoke-test двух принципалов выполняется владельцем отдельно.

### Одноразовый профиль и секретная комната

Одноразовый профиль создаётся только для персонального приглашения в секретную
комнату. Приглашение одноразовое, персональное и имеет TTL.

Правила текущего решения:

- reconnect grace period — 2 минуты;
- отдельные устройства для одного одноразового профиля не поддерживаются;
- аудио- и видеозвонки в одноразовых комнатах текущим контрактом не
  предусмотрены; frontend не показывает эти действия;
- участник может выйти сам, не уничтожая комнату для остальных;
- закрытие комнаты создателем уничтожает комнату для всех;
- при выходе участника уничтожаются его временные ключи и локальные данные;
- если участник не вернулся за 2 минуты, его локальная сессия считается закрытой;
- клиент хранит локальный deadline/epoch и при следующем запуске самостоятельно
  очищает истёкшую сессию; постоянная серверная команда очистки не требуется;
- сообщение, файл и ключи одноразовой комнаты не сохраняются в обычном
  PocketBase/MinIO-контуре;
- медиа одноразовой комнаты живут только в памяти устройства и уничтожаются при
  выходе, закрытии комнаты или истечении reconnect-периода;
- push содержит только нейтральный сигнал без текста, имени комнаты и состава
  участников;
- одноразовые данные не включаются в резервные копии.

Существующий код с названиями `isPrivate`/`isEphemeral` не реализует этот
контракт: он использует обычные PocketBase/MinIO и не должен считаться
прототипом готового одноразового режима.

Нельзя технически гарантировать удаление скриншотов, экспортированных ключей,
данных отключенного устройства или сетевых метаданных провайдера. Реализация
должна гарантировать уничтожение серверных временных данных, ключей и локальных
кэшей, которыми управляет приложение.

## Медиа

Для постоянных профилей приложение шифрует медиа на клиенте до отправки в
PocketBase. PocketBase хранит запись и передает файл в соответствующий MinIO
bucket через S3-compatible storage. Dev и Prod никогда не используют общий
bucket или общий service account.

Одноразовые медиа идут по отдельному runtime-пути и не должны вызываться через
обычную коллекцию `media` или попадать в MinIO.

## Кэширование списка чатов (cache-first) и очистка при logout

Локальная реализация frontend, без утверждений о browser/runtime-поверке:

- список чатов после reload читается из постоянного IndexedDB-кеша мгновенно
  (cache-first), а серверная синхронизация, включая N+1-запросы последних
  сообщений, выполняется в фоне; кеш хранит только raw-данные (ciphertext
  `last_message`), расшифрованный plaintext в IndexedDB не сохраняется;
- имя IndexedDB-базы детерминированно выводится из `userId` и полного origin
  PocketBase URL, поэтому dev/prod, http/https и разные порты не разделяют кеш;
  legacy host-based базы (созданные до перехода на origin) чистятся best-effort;
- malformed кеш валидируется `roomWithMembersSchema` и обрабатывается как cache
  miss — повреждённые данные не попадают в decrypt/UI; при `isDecrypted:false`
  или ошибке расшифровки ciphertext не показывается (подменяется пустой строкой);
- session generation guard (`sessionGuard`) защищает от записи устаревших
  async-ответов в QueryClient/IndexedDB после logout; при logout
  `sessionCleanup` отменяет (`cancelQueries`) и удаляет (`removeQueries`)
  чувствительные query-ключи, а `roomListDb.clear` очищает постоянный кеш.

Проверено unit-тестами (замоканы PocketBase/IndexedDB и seam'ы, без Dev/Prod API
и без реальной IndexedDB): см. `TESTING_PLAN.md`, «Срез 8». Реальное поведение
IndexedDB/Dexie, расшифровка на реальных ключах, cancel сетевых fetch'ов
RealtimeGateway при logout и полный цикл cache-first при сетевых задержках
требуют browser/runtime E2E и НЕ проверялись. Это не является заявлением о
release readiness или проверенном Dev/Prod-контуре.

завершение звонка с обеих сторон, приватные профили без имени/avatar/username,
одноразовую комнату без кнопок звонка и одно увеличение unread на одно новое
сообщение.
