# Архитектура групповых чатов (Groups v2)

В основе логики групповых чатов лежит строгое разделение аккаунтов на 2 типа (уровня): **Открытые (Public)** и **Закрытые (Private / Ghost)**. Смешивание аккаунтов разных типов в одной группе категорически запрещено.

---

## 1. Открытые группы (Создатель — Открытый аккаунт)

- **Тип создателя**: `profile_type === "public"`
- **Кто может быть участником**: Только открытые аккаунты.
- **Способы приглашения**:
  1. Глобальный поиск по никнейму/email в приложении.
  2. Инвайт-ссылка (Link) / QR-код.
- **Режимы группы (Visibility / Permissions)**:
  - **Public (Публичная)**: Любой текущий участник группы имеет право генерировать инвайт-ссылки или добавлять других открытых пользователей через поиск.
  - **Private (Приватная)**: Исключительное право на генерацию ссылок и добавление пользователей принадлежит только Администратору/Создателю.

## 2. Закрытые группы (Создатель — Закрытый аккаунт)

- **Тип создателя**: `profile_type === "private"`
- **Кто может быть участником**: Только закрытые аккаунты. Открытые аккаунты не могут быть добавлены.
- **Способы приглашения**:
  1. Только через **инвайт-ссылку (Link) / QR-код**. Так как закрытые аккаунты скрыты из глобального поиска по соображениям безопасности, добавить их через поиск невозможно. 
  2. Передача ссылки происходит out-of-band (в другом мессенджере) или через уже существующий закрытый P2P-чат.
- **Режимы группы (Visibility / Permissions)**:
  - Строго **Private**. Только Администратор/Модератор имеет доступ к генерации инвайт-ссылок.

---

## 3. Механизм E2E-шифрования в группах (Симметричный ключ в URL хэше)

### Генерация и передача ключа:
1. **Создание группы**: Модератор локально (в браузере) генерирует случайный симметричный ключ (AES-GCM), который будет использоваться для шифрования всех сообщений в этой группе. Этот ключ никуда не отправляется в открытом виде.
2. **Создание инвайт-ссылки**: Приложение модератора обращается к серверу для создания записи `invite` (сервер генерирует случайный `token` и привязывает его к `room_id`). 
3. **Формирование URL**: Приложение склеивает серверный токен и локальный Room Master Key в формате URL с хэшом.
   - Пример: `https://nemo.app/join/SERVER_TOKEN#ROOM_MASTER_KEY`
   - *Почему хэш `#`?* Фрагмент после решетки (`#`) **никогда не отправляется на сервер** браузером. Таким образом, сервер знает только `SERVER_TOKEN`, но не знает ключ расшифровки.
4. **Присоединение**: 
   - Новичок переходит по ссылке.
   - Браузер отправляет на сервер `SERVER_TOKEN`.
   - Если токен валиден и не протух, сервер добавляет новичка в список участников комнаты `room_members`.
   - Приложение новичка берет `ROOM_MASTER_KEY` из URL-хэша, зашифровывает его своим публичным ключом и сохраняет в свою локальную базу и на сервер.

---

## 4. Срок жизни и лимиты инвайт-ссылок (Гибридный подход)

### Открытые группы (Public)
1. **Ссылка Модератора / Создателя**:
   - **Срок жизни**: Постоянная (безлимитная по времени).
   - **Кол-во использований**: Неограниченно.
2. **Ссылка Участника (если включено разрешение)**:
   - **Срок жизни**: Ограниченный (например, 24 часа).
   - **Кол-во использований**: Максимум 1 раз.

### Закрытые группы (Private)
1. **Гибридный лимит (Устанавливается при создании)**:
   - **Срок жизни**: Настраиваемый (15 мин, 1 час, 24 часа).
   - **Кол-во использований**: Задается модератором (строго 1 или более).
