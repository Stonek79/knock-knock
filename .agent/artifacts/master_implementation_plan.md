# Пофайловый План Рефакторинга: Metadata Resistance & Channels

Этот документ представляет собой технический пофайловый план реализации новой архитектуры (Бизнес/Приватные профили, Sealed Sender, Key Vault, Каналы, WebRTC и Push).

## 1. База Данных (Инфраструктура)
- **`infra/home/pb_schema.json` (Схема БД)**
  - *`users`*: Удалить `role` (оставить `admin` только в `_superusers`). Добавить `profile_type` (`public` | `private`), `public_profile_key` (text), `encrypted_profile` (json), `key_vault` (json).
  - *`messages`*: УДАЛИТЬ `sender_name`, `sender_avatar`. (Поле `sender` остается опциональным для проверки прав).
  - *`room_members`*: УДАЛИТЬ `user_name`, `user_avatar`. Участники идентифицируются только по UUID.
  - *`rooms`*: Добавить `inactivity_timer` (number). Сделать поле `type` поддерживающим каналы (`public_channel`, `private_channel`, `direct`, `group`, `ephemeral`).
  - *`media`*: Удалить метаданные об оригинальном файле.
  - *`call_logs`*: Удалить массив `participants` из открытого вида, перенести в `encrypted_metadata` (json).

## 2. Глубокий рефакторинг Фронтенда (По следам типов и открытых полей)
**Аудит выявил ~70 файлов, зависящих от открытых данных (`display_name`, `avatar`, `role`, `sender_name`).** 

### 2.1. Репозитории и Схемы
- **`app/src/lib/types/pocketbase-types.ts` & `app/src/lib/schemas/*.ts`**
  - Убрать `role`, `sender_name`, `sender_avatar` из типов. Добавить `encrypted_profile`.
- **`app/src/lib/repositories/mappers/userMapper.ts` & `roomMapper.ts` & `messageMapper.ts`**
  - Это **ядро изменений**. Мапперы больше не могут просто мапить `record.display_name`.
  - Они должны использовать сервис `ProfileCryptoService` (или `KeyVaultService`), чтобы подставить расшифрованное имя из локального хранилища (IndexedDB/Zustand), сопоставляя UUID.
- **`app/src/lib/repositories/user.repository.ts` & `auth.repository.ts`**
  - Изменить методы `updateProfile`. Если профиль `private`, шифровать `display_name` и `avatar` ключом `Profile Key` перед отправкой в БД.

### 2.2. Авторизация и Сейф (Key Vault)

- **`app/src/stores/auth/index.ts`**
  - Убрать проверки `user.role === 'admin'`. Вместо этого проверять факт логина как `admin` (через состояние PocketBase).
  - Загружать и хранить расшифрованный `Key Vault` в памяти.

### 2.3. Чаты и Sealed Sender
- **`app/src/lib/services/chat-crypto.ts` & `message.ts` & `optimistic.ts`**
  - Изменить логику `encryptMessage`: перед шифрованием `content`, упаковывать туда `{ text, sender_name, sender_id, sender_avatar }`.
  - Изменить `optimistic.ts`: не слать `sender_name` на сервер, а паковать локально.
- **UI Чатов (`MessageList`, `MessageBubble`, `RoomHeader`)**
  - Рендеринг будет опираться на обновленные объекты, выданные мапперами, так что прямые изменения в UI будут минимальны (только избавление от `role`).

### 2.4. Звонки, WebRTC (LiveKit)
- **`app/src/features/calls/...`** (Будущие или существующие модули звонков)
  - Сервер генерирует токен LiveKit, где `participantName` = `UUID` (чтобы облако LiveKit ничего не знало о людях).
  - В UI звонка фронтенд подтягивает реальные имена из локального `Key Vault` по этому UUID.
- **`call_logs`**: Фронтенд будет шифровать массив участников ключом комнаты и сохранять в `encrypted_metadata`.

### 2.5. Push-Уведомления и Web Push
- **Service Worker (`sw.js`)**
  - Сервер будет рассылать "Слепой Пуш" (Blind Push): сигнал `{"type": "new_message", "room_id": "..."}`.
  - Service Worker должен "будить" приложение или обращаться к локальному хранилищу ключей для расшифровки сообщения и показа настоящего имени в уведомлении (Notification API).

### 2.6. Модерация (Репорты) и AdminLayout
- **`app/src/features/admin/AdminLayout/index.tsx` & `UserList/index.tsx`**
  - Полностью изолировать этот модуль. Он доступен только при входе через `pb.admins.authWithPassword`.
- **Модерация (`message_reports`)**:
  - При отправке жалобы на пользователя, фронтенд "прикладывает" к репорту уже расшифрованный фрагмент сообщения в открытом виде для админа (так как админ не имеет ключей для расшифровки комнаты).

## 3. Каналы (Channels & Chats)
- **Открытые Каналы**: Только для Бизнес-аккаунтов. QR публичен. Удаляет Админ/Создатель.
- **Закрытые Каналы**: По инвайту. Удаление каскадное. *Таймер неактивности* (Хук `onTicker` в `infra/home/pb_hooks/` будет стирать неактивные каналы).
- **Чаты**: Публичные (Открытый с Открытым) и Приватные (Эфемерные, Инкогнито с Инкогнито).

## 6. Стратегия Рефакторинга и Деплоя (Environment Isolation)
Поскольку изменения схемы базы данных деструктивны (удаление старых полей `sender_name`, `display_name` и добавление новых), мы не можем применять их к рабочей базе до полной готовности фронтенда. 

**Выбранная стратегия: Изоляция сред разработки (Dev Isolation)**
1. **БД Dev-режима**: Мы накатываем новую (измененную) схему `pb_schema.json` **только** на локальную/дев-базу PocketBase. Рабочая/Prod база остается нетронутой.
2. **Слом и Починка Фронтенда**: Локальный фронтенд, подключенный к `dev`-базе, естественно, сломается (мапперы перестанут находить старые поля). Мы планомерно переписываем весь фронтенд согласно этому плану, работая исключительно с `dev`-окружением.
3. **QA и Тестирование**: После завершения рефакторинга мы полностью тестируем приложение (Звонки, Пуши, Чаты) в Dev-режиме.
4. **Релиз на Prod**:
   - Поскольку приложение **еще не в продакшене** (или данные тестовые), мы применяем измененный `pb_schema.json` на Prod-сервере.
   - Деплоим обновленный фронтенд.
   - *Примечание по миграции*: Старые тестовые сообщения потеряют имена отправителей, а старые профили окажутся пустыми. Это нормально для текущей стадии (тестовая БД). В будущем такие изменения производились бы по стратегии "Expand and Contract" (добавление новых полей без удаления старых на переходный период).
