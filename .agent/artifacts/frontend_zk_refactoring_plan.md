# План реализации следующего этапа: Zero-Knowledge Frontend

Согласно мастер-плану, фаза работы с сервером (БД, хуки, RLS) **завершена**. Теперь мы переходим к самому масштабному и важному этапу — **рефакторингу Frontend-части** для поддержки архитектуры "Zero-Knowledge" (Шифрование метаданных, Бизнес/Приватные профили, Sealed Sender).

Мы будем двигаться "снизу вверх": от Data Layer (типы, мапперы, криптография) к State Management (Zustand) и, наконец, к UI слою.

---

## Этап 3.1: Data Layer и Криптография (Основа)

1. **Типы PocketBase (`pocketbase-types.ts`, `schemas/*.ts`)**:
   - Отразить изменения БД: сделать `display_name` и `avatar` опциональными (`?string`).
   - Добавить новые поля `profile_type`, `public_profile_key`, `encrypted_profile`, `key_vault`, `encrypted_metadata`, `inactivity_timer`.
   - Удалить `sender_name`, `sender_avatar`, `user_name`, `user_avatar`, системную `role`.

2. **Крипто-модуль (`ProfileCryptoService` / `VaultService`)**:
   - Реализовать логику генерации `Profile Key` и шифрования/дешифрования локального `KeyVault` с помощью мастер-пароля.
   - Реализовать AES-GCM шифрование/дешифрование `encrypted_profile`.

3. **Репозитории и Мапперы (`userMapper.ts`, `roomMapper.ts`, `messageMapper.ts`)**:
   - **User Mapper**: Если `profile_type === 'public'`, брать `display_name` напрямую. Если `private` — расшифровывать из `encrypted_profile`.
   - **Message/Room Mapper**: Прекратить чтение `sender_name`/`sender_avatar`. Использовать UUID и реестр профилей (Vault) для подтягивания имен.

---

## Этап 3.2: Авторизация и Управление Состоянием (State)

1. **Авторизация (`stores/auth/index.ts`, `auth.repository.ts`)**:
   - Убрать зависимость от `user.role === "admin"`. Перейти на проверку `pb.authStore.isAdmin`.
   - **LoginForm / RegisterForm**: Внедрить шаг ввода мастер-пароля (или использовать пароль от аккаунта) для дешифрации `KeyVault` при логине.
   - Для регистрации добавить шаг выбора типа аккаунта (Public/Private) и генерацию стартовых ключей.

2. **Локальный кэш контактов**:
   - Создать/обновить стор для хранения расшифрованных профилей Инкогнито-пользователей в оперативной памяти (чтобы мапперы и UI не перешифровывали одни и те же данные на каждый рендер).

---

## Этап 3.3: Настройки и Управление Профилем (UI)

1. **Privacy & Profile Settings**:
   - Добавить переключатель "Тип аккаунта" (Бизнес / Инкогнито).
   - Настроить механизм перешифровки: при переходе в Инкогнито — очищать открытые поля в БД и обновлять `encrypted_profile`.
   - Обновление пароля (`ChangePasswordForm`) должно перешифровывать `KeyVault`.
   - Удаление аккаунта: уничтожение всех ключей комнат и Vault на сервере.

2. **Admin Panel (`features/admin/`)**:
   - Убрать все привязки к `user.role`. Модуль доступен только через `pb.admins.authWithPassword`.

---

## Этап 3.4: Чаты, Sealed Sender и WebRTC

1. **UI Чатов и Списка Диалогов**:
   - Оптимистичный рендеринг: убрать отправку открытых `sender_name`/`avatar` в API.
   - В UI отображать расшифрованные имена из локального стора/кэша.

2. **Звонки и Логи (`features/calls/`)**:
   - Заменить открытый список `participants` на дешифруемую структуру `encrypted_metadata`.
   - WebRTC (LiveKit): передавать обезличенные UUID в токенах.

3. **Push-Уведомления (Blind Push)**:
   - Обновить Service Worker (`sw.ts`) для пробуждения по Blind-событию (содержит только `roomId`).
   - SW должен иметь доступ к ключам для дешифровки и локального показа "Вам пришло сообщение от ...", не сливая текст в Apple/Google.
